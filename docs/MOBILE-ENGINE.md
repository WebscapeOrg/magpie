# Native iPhone engine

`magpie-mobile` packages the shared Rust engine as an Apple static library. Its C interface in `include/` owns opaque engine/request/result handles; Swift's `NativeEngine` actor in the sibling `magpie-ios` repository handles asynchronous completions and releases results. No desktop executable or JSON-RPC subprocess runs on iOS.

The engine uses one bounded executor with a Tokio `LocalSet`, at most 32 admitted requests, 32 MiB per frame and 64 MiB of aggregate admitted input. Responses preserve the backend's method-specific bounds. Admission and lifecycle state are separate from provider completion: cancellation or a Swift timeout cannot release a mutation's ownership lock while its underlying future is still running. Suspension refuses new writes and drains admitted work; closing waits for quiescence.

The host supplies its app-owned storage roots and Keychain identity. iOS credentials are device-only, available after the first unlock and isolated by client/account. Private files reject unsafe ancestry and links. Attachments copied into a draft have independent ownership so closing another reader/editor cannot delete them. Account removal targets that account's credentials and private records, preserving siblings.

`engine.info` reports ABI, backend API, development version and the build's source identity. `magpie-ios/scripts/build-engine.sh` computes that identity from the engine source, builds both Apple architectures and writes the matching app resource. A mismatched native library fails before account access. The identity is a compatibility guard, not a signature or a substitute for release checks.

Gmail operations use the same provider and durable state machinery as Linux. OAuth uses the phone's own Google iOS client with PKCE/state, not a copied desktop secret or refresh token. Sending and edits retain ownership and retry identities through suspension and uncertain responses. Calendar operations belong to Skylark. Model output does not authorize sending.

The main machine hosts AI, authoritative snooze mutations and silent APNs wake-ups. The phone uses the narrow paired HTTPS API in `src/backend/phone`; it cannot send arbitrary backend methods to the main machine. Pairing intersects device access with current account ownership, and revocation removes access. AI requests preserve their selected message/draft context and parent identity; changes are reviewed on the phone before application.

Unit and integration tests live with their Rust modules and the iPhone Core package. Native simulator checks additionally cover the actual C ABI, Keychain, private filesystem, lifecycle and WebKit/JavaScript sanitization boundaries with synthetic fixtures. File protection and operating-system lifecycle behaviour require physical-device evidence.

Magpie for iPhone 0.1.28 and later raise new-mail alerts on the phone and register with `notifications: false`, so the main machine sends them no visible alerts. The paired `/v1/notifications` API still lists the mail alerts the main machine retained earlier, opens one and marks it read. Every returned alert requires all of its account owners to remain in the paired device’s current account set. The private archive is written before an APNs attempt, deduplicates retries by alert identity and shares read state between authorized devices. It records the attempt time; APNs acceptance does not prove display on the phone. Calendar reminders scheduled by the phone keep their history locally.

## Bounded background refresh

The phone registers `net.anotherdave.magpie.refresh` before launch completes, submits a `BGAppRefreshTaskRequest` no earlier than half an hour later, and accepts the fixed `magpieRefresh: 1` silent-push hint. Both triggers share one refresh run. iOS decides whether and when either runs; this is not continuous mail service or a promised interval. Foreground entry cancels and waits for background work before restoring normal mail operations.

`engine.backgroundRefresh` is an empty-parameter, mobile-host-only operation. It runs only while the host is inactive, holds exclusive operation ownership, reads registered Gmail accounts, and uses the existing quota-paced receive/checkpoint machinery without delivering local edits or waking the outbox. Paused accounts make no provider requests. Each account gets up to 18 seconds of receive work; the host bounds the entire operation to 20 seconds. Cancellation drops that receive future and allows up to two seconds for local disk work to drain, including database opens not yet inserted in the store map. Failure to drain returns an error; atomic database transactions retain the normal safety guarantees if iOS suspends during disk work. No background result claims a completed history check merely because a refresh was requested.

Each account's background result also carries `alerts`, the same read-only snapshot that the active-only `engine.mailAlerts` returns for every registered Gmail account: `ready` (the Inbox has been listed), `paused`, `inbox` (up to 50,000 Inbox ids, newest first) and `unread` (up to 20,000 unread Inbox messages with id and date, newest first, with sender and subject for the newest 2,000). The engine makes no alert decision. Swift keeps the decision state privately on the phone and follows the main machine's former rules: the first ready look is silent, each message alerts once, and only unread Inbox mail with a current description counts, because the curated Inbox shows only that mail. A message already known stays quiet if it leaves the Inbox and returns within 30 days or is marked unread later, and unread mail dated more than three days before the previous look stays quiet when it enters the Inbox, as the main machine kept quiet about mail it already stored. A late alert names when the mail arrived. Mail that waits more than three days for its description does not alert. Foreground checks update that state and the badge without announcing. A background run posts one local alert for the new mail it finds after the refresh, naming the sender and description for a single message, then fetches descriptions for recent unread mail that has none and posts a second alert only for mail those descriptions make ready. Each alert is recorded in a private history file separate from calendar history.

Without a Claude API key, Swift uses the remaining 25-second overall budget to fetch already-prepared descriptions from the main machine and save them privately for offline display. With a key it calls `engine.backgroundDescribe` instead, provided no more than 6 seconds have passed, so the call's 16-second bound ends before the 25-second cut-off. It does not start snooze mutations or mail sending in either path. Foreground mail reloads the description cache after background work finishes. The native build identity pins this host-only method; it is not added to the desktop RPC surface.

## Descriptions written on the phone

A phone that holds Dave's own Claude API key writes Inbox descriptions itself with the same rules, validation and storage as the main machine (`src/inbox/describe.rs`). `src/inbox/claude.rs` calls `POST https://api.anthropic.com/v1/messages` with `claude-haiku-5-5`, low effort and no tools, through a client with no proxy, no redirects, HTTPS only and bounded replies. The key is a `ClaudeApiKey` credential in the device-only Keychain (`AfterFirstUnlockThisDeviceOnly`, not synchronised). It is read from the Keychain for each batch of messages and each status check, sent only in a sensitive `x-api-key` header, and never returned, logged or stored elsewhere. Only standard `sk-ant-api…` keys are accepted.

- `ai.setKey {key}` checks the key with `GET /v1/models/claude-haiku-5-5` before saving it and refuses a malformed key before any request. `ai.removeKey {}` deletes it. `ai.keyStatus {}` returns `{present, model, problem}` and never the key.
- `engine.overviews` and `engine.overviewSettings` take the same parameters and return the same shapes as the main machine's `/v1/overviews` and `/v1/overview-settings`, so the app switches writer without a second code path. A request names at most 100 ids to read and at most 4 to describe. A page returns the stored descriptions for those ids only. Rows also carry `attempts`.
- `engine.backgroundDescribe {accounts:[{accountId, ids}]}` runs only while the host is inactive. The app names at most 20 unread Inbox messages per account that have no saved description, so mail the main machine already described is not described again. The engine describes the first 4 of them that are due, so messages that failed or are still being described do not hold back the ones behind them unless nearly all 20 are in that state. It starts no further account once fewer than 3 of its 14 seconds remain, and the host bounds the call to 16 seconds. A description still being written when the call returns is saved only if iOS keeps the app awake long enough; otherwise the message is asked about again later.

Cost and failure rules:

- Each message is read, prepared and described on its own, so a message that cannot be read, prepared or described fails alone. A message takes one to three free token counts and two or three passes (the third only when the second answer fails validation), and its passes start again without its PDF if Claude refuses the PDF. Its media comes first with a cache point and the instructions last, so the second and third passes read the media from the prompt cache.
- Before a message is sent, `POST /v1/messages/count_tokens` counts it without charge. PDFs, then pictures, are dropped until it fits within 80,000 tokens, and a message too long without them fails. Recipient and attachment lists are cut to 50 entries each. With the rules and the earlier passes' answers added, a request stays below Haiku 5.5's 100,000-token price step. The phone cannot render PDF pages, so it sends a PDF as a document block; if Claude refuses a PDF, the message is described without it.
- Spending is counted from the token usage Claude reports and stops for the day at about $0.50, or after 1,500 calls including counts. The day follows UTC. A request cut off when iOS suspends the app may still be billed without being counted, so the spend limit on the key's workspace in the Claude Console remains the firm limit.
- A missing, refused or invalid key, a billing problem, a rate limit, an unreachable service or the daily limit refuses before any message is claimed: `engine.overviews` then answers `accepted: false` with `problem`, and the app stops asking but keeps reading pages. An invalid or refused key stops requests until Dave replaces it; billing waits an hour; rate limits and an unreachable service wait five minutes. A failure from a request made with a key that has since been replaced is ignored.
- A message that fails three times when Claude was asked about it is not asked again automatically on the phone. Failures while reading or preparing mail, failures of the whole batch, and service failures (Claude, Gmail, network or storage) do not count. Retry in Settings forgives every failed message in every account, so the following polls ask about them again. The main machine and Magpie on Linux keep their 15-minute retry. Known limit: a message for which Claude keeps answering with a server error or a rate limit counts as a service failure each time, so it is never capped and pauses describing for five minutes each time.
- When the phone writer has no saved settings for an account, and whenever a key is saved, the app sends this iPhone's pause and remote-image settings first. The main machine is told only of a pause, because its settings are shared with Magpie on Linux.

Model output stays untrusted: descriptions pass the same validation as the main machine's and cannot route, send or change mail.

A paired phone opts into `backgroundRefresh` independently of visible notification permission. `/v1/status` advertises support so new phones can still register with older engines. The main machine intersects the pairing account set with current accounts and the phone’s selected accounts. It sends only a fixed hint, never mail content, with `apns-push-type: background`, priority 5 and a fixed collapse identifier. A private per-device journal records each attempt before the request and coalesces later revisions for at least half an hour. Failed attempts also consume that interval. Visible alerts follow the device's `notifications` flag, which current phones always send as false.

Apple documents discretionary scheduling in [background task guidance](https://developer.apple.com/documentation/backgroundtasks/refreshing-and-maintaining-your-app-using-background-tasks) and [background push guidance](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app). Simulator checks cannot establish physical-device delivery, scheduling frequency or operation before the first device unlock.
