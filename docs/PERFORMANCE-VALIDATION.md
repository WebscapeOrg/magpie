# Performance and offline-mail release checks

The local implementation is described in [LOCAL-MAIL.md](LOCAL-MAIL.md). API 8 remains unreleased; do not replace the pinned binary or publish a release until these checks pass. Use synthetic mail and controlled provider endpoints for mutation/send tests.

## Ownership and automation

This is an agent verification runbook, not a checklist for Dave. The performance implementation and this automation stay in a draft PR until the required results are available. Agents investigate failures, repair the fixtures or implementation as appropriate, rerun the affected gates and publish the evidence. Do not transfer ordinary test execution or benchmark analysis to Legwork.

The `Performance verification` GitHub Actions workflow runs on relevant PR changes and supports manual dispatch. It uses ephemeral hosted Linux runners, synthetic data, a private test HOME/XDG tree and private DBus sessions, with read-only repository permissions and no production secrets. The `ci` job runs Rust, JavaScript, source, portable shell, native QML security, standalone composition/native host and actual backend API checks. Offline storage recovery and subprocess cancellation also run as independent gates without sockets or DBus, so a blocked integration environment still collects those results. Every gate has a separate log and status; failures do not prevent later independent gates from running. JSON results and a summary are retained as workflow artifacts even on failure. The existing CI `Released backend gate` verifies the actual exact pinned release separately.

The `benchmarks` job builds first, then runs measurements sequentially: original-commit versus working-tree list population/navigation/update, 100,000-message database search with and without background writes, and the separate million-message scale case. It retains raw samples, source hashes, runtime details and the measurement boundaries. Hosted timings describe that runner; they are not desktop acceptance evidence.

The same runner works locally with `make verify-performance`. Use `VERIFY_PROFILE=desktop` on an authorized Omarchy development runner to include the full `make validate` and real Quickshell process bridge, or `VERIFY_PROFILE=benchmarks` for the measurements. `VERIFY_OUTPUT=/absolute/new/directory` chooses a fresh report directory. `python3 scripts/verify-performance.py --profile desktop --preflight-only --output /tmp/magpie-preflight` checks sockets, ownership, private DBus and installed tools without running the suite. Missing capabilities are recorded as blocked and return nonzero; no security check is disabled to obtain a pass.

The desktop/recovery scenarios below are the agent's acceptance work. Existing unit/component fixtures cover parts of them; the runner does not claim that those fixtures establish complete provider recovery, physical compositor timing or screen-reader usability. Any missing scenario requires an automated fixture or an agent-operated synthetic desktop session before its gate can be marked passed. HTTP/2/gzip and compiler tuning are separate experiments for a future settings change, not requirements for shipping the unchanged transport/compiler configuration.

The independent `qml-components` gate runs each QML fixture that does not import the native model bridge, retaining its own process result and log. Fixtures that import `NativeIntentFixture.js` are listed explicitly under `nativeBridgeRequired`; they remain covered by the complete `test-qml` gate and are not counted as component passes. This allows interaction regressions to run when local sockets are unavailable without replacing provider or resource-security tests. Rust and full desktop validation also require a working PDF sandbox: the workflow installs Bubblewrap and Poppler, and preflight checks that the isolated worker can start so missing tools cannot make conditional PDF tests look like complete security evidence.

The independent `shell-independent` gate runs the 35 shell/Python files that need no listeners or DBus, plus the seven public-HTTP policy cases. The complete `test-shell-portable` target still includes all 38 original files, including notification routing, real curl refusal and HTTP/TLS integration. A passing independent gate cannot establish those network or DBus boundaries. Both targets use the same maintained commands; the runner confines their state to temporary HOME/XDG directories.

## Desktop and recovery checks

Exercise a development instance through the documented development launch flow. Preserve real accounts and stored data. Prefer dedicated test accounts or synthetic fixtures for every destructive action.

1. Open a previously synchronized inbox with networking unavailable. Verify lists, bodies, labels and counts appear from local state and that cached mail remains readable after authorization expires.
2. Stop the test backend during inventory, a history page and a body download. Restart it and verify it resumes without declaring incomplete coverage complete or deleting unvisited rows. Exercise expired history and low-space refusal using controlled fixtures.
3. Queue read/unread, star/unstar and folder changes offline. Check immediate local state, queued Undo, rapid reversals, reconnect reconciliation and visible conflicts after a server-side deletion.
4. With a controlled send recorder, explicitly press Send offline, restart before transmission, then reconnect. Verify one delivery. Interrupt a send after transmission begins and verify the recovered state is unknown with no automatic retry. Cancel during preflight and verify the recorder receives nothing.
5. Restore a draft with retained file handles, switch accounts and attempt foreign-draft handle reuse. Confirm the wrong account/draft cannot obtain the bytes and that the owning draft still works.
6. Switch calendar months and accounts while responses are pending. Confirm the selected range stays visible, newer empty ranges do not resurrect removed events, and bar/reminder reads reuse cached ranges. Check recurrence and DST cases across Google, Graph and CalDAV.
7. Use the new status and send controls by keyboard, screen reader and enlarged text. The synthetic Qt screenshots establish component layout at one scale; they do not establish whole-desktop accessibility or every active Omarchy theme.

## End-to-end performance acceptance

Measure input acknowledgement, completed visible paint and cold local inbox startup separately. Record hardware, Qt/backend versions, viewport/theme/scale, corpus sizes, binary/source hashes and whether OS caches were warm. The targets remain p95 ≤50 ms input acknowledgement, ≤100 ms warm navigation, ≤200 ms large HTML, ≤200 ms 100,000-message local search, ≤1 s cold local inbox, and ≤20% foreground degradation during background work. Measure one million messages as a separate scale case. Database-only and offscreen-frame results do not certify all these targets.

The reproducible component harnesses are in [benchmarks/mail/README.md](../benchmarks/mail/README.md). Run them after builds have stopped. Include input handling, RPC and actual window painting in the desktop run, and compare foreground latency with background sync idle and active. Report a miss rather than substituting callback completion for visible paint.

## HTTP transport experiments

Current reqwest features do not opt into HTTP/2 or gzip. Leave the release settings unchanged until representative controlled-server measurements compare the existing client with each feature independently and together. Record connection reuse, negotiated protocol, wire bytes, concurrency, p50/p95 and total throughput. Repeat on a constrained connection and with background sync active. Verify deadlines, decompressed-size bounds, credential origin confinement, TLS and redirects before accepting a change. Do not infer a gain from protocol support alone.

The compiler-profile harness compares current size optimization with `opt-level=3` using identical synthetic parsing/rendering inputs. It checks semantic equivalence and records binary hashes. Treat it as a CPU diagnostic; repeat the complete desktop path before changing the release profile. The implementation keeps the existing compiler and transport settings.
