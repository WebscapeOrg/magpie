# Native iPhone engine

`magpie-mobile` packages the shared Rust engine as an Apple static library. Its C interface in `include/` owns opaque engine/request/result handles; Swift's `NativeEngine` actor in the sibling `magpie-ios` repository handles asynchronous completions and releases results. No desktop executable or JSON-RPC subprocess runs on iOS.

The engine uses one bounded executor with a Tokio `LocalSet`, at most 32 admitted requests, 32 MiB per frame and 64 MiB of aggregate admitted input. Responses preserve the backend's method-specific bounds. Admission and lifecycle state are separate from provider completion: cancellation or a Swift timeout cannot release a mutation's ownership lock while its underlying future is still running. Suspension refuses new writes and drains admitted work; closing waits for quiescence.

The host supplies its app-owned storage roots and Keychain identity. iOS credentials are device-only, available after the first unlock and isolated by client/account. Private files reject unsafe ancestry and links. Attachments copied into a draft have independent ownership so closing another reader/editor cannot delete them. Account removal targets that account's credentials and private records, preserving siblings.

`engine.info` reports ABI, backend API, development version and the build's source identity. `magpie-ios/scripts/build-engine.sh` computes that identity from the engine source, builds both Apple architectures and writes the matching app resource. A mismatched native library fails before account access. The identity is a compatibility guard, not a signature or a substitute for release checks.

Gmail operations use the same provider and durable state machinery as Linux. OAuth uses the phone's own Google iOS client with PKCE/state, not a copied desktop secret or refresh token. Sending and edits retain ownership and retry identities through suspension and uncertain responses. Calendar operations belong to Skylark. Model output does not authorize sending.

The phone does not connect to the main machine. It writes descriptions and answers Ask Magpie with Dave's own Claude API key, as described below. Snooze runs in the phone's own engine with the same Rust code as Linux: the schedule is kept in Gmail as hidden labels, so the phone and Magpie on Linux share it. AI requests preserve their selected message/draft context and parent identity; changes are reviewed on the phone before application. Magpie for iPhone 0.1.31 and earlier paired with the main machine over a narrow HTTPS API on port 3450 for silent wake-ups, descriptions, questions and alert history. Magpie for iPhone 0.1.32 removed that client and asks the main machine to forget its pairing, and the desktop engine no longer serves that API.

Unit and integration tests live with their Rust modules and the iPhone Core package. Native simulator checks additionally cover the actual C ABI, Keychain, private filesystem, lifecycle and WebKit/JavaScript sanitization boundaries with synthetic fixtures. File protection and operating-system lifecycle behaviour require physical-device evidence.

Magpie for iPhone raises new-mail alerts on the phone and keeps their history locally, as it does for the calendar reminders it scheduled. Alerts the main machine kept for earlier versions are not shown.

## Bounded background refresh

The phone registers `net.anotherdave.magpie.refresh` before launch completes, and submits a `BGAppRefreshTaskRequest` no earlier than half an hour later. iOS decides whether and when it runs; this is not continuous mail service or a promised interval. Foreground entry cancels and waits for background work before restoring normal mail operations.

`engine.backgroundRefresh` is an empty-parameter, mobile-host-only operation. It runs only while the host is inactive, holds exclusive operation ownership, reads registered Gmail accounts, and uses the existing quota-paced receive/checkpoint machinery without delivering local edits or waking the outbox. Paused accounts make no receive requests, although the snooze tick below still returns their due snoozes and looks for new ones. Each account gets up to 18 seconds of receive work; the host bounds the entire operation to 20 seconds. Beside the receive work, inside the same exclusive operation, the host runs `inbox.tick` limited to 5 seconds and cut off after 8, so due snoozes return to the Inbox without another device running. The tick's Gmail requests count as foreground, so a receive request that meets one in flight, including the fetch of a new message, gives way without being put off and is asked again every 250 ms within the receive bound. In effect the receive follows the tick, and the reply waits for both. A snooze change not yet on the wire when the tick is cut off is abandoned rather than sent later; one already sent may still land. The tick's result is the reply's `snoozes` field (`woke` and `failures`, or `error`). That tick is the only Gmail write a background run makes; the inactive engine refuses `inbox.tick` as a call of its own, and Swift's background guard in `NativeEngine` does not admit it. The tick returns due mail before it looks for snoozes made on other devices, so a short one still wakes mail. Cancellation drops that receive future and allows up to two seconds for local disk work to drain, including database opens not yet inserted in the store map. Failure to drain returns an error; atomic database transactions retain the normal safety guarantees if iOS suspends during disk work. No background result claims a completed history check merely because a refresh was requested.

Each account's background result also carries `alerts`, the same read-only snapshot that the active-only `engine.mailAlerts` returns for every registered Gmail account: `ready` (the Inbox has been listed), `paused`, `inbox` (up to 50,000 Inbox ids, newest first) and `unread` (up to 20,000 unread Inbox messages with id and date, newest first, with sender and subject for the newest 2,000). The engine makes no alert decision. Swift keeps the decision state privately on the phone and follows the main machine's former rules: the first ready look is silent, each message alerts once, and only unread Inbox mail with a current description counts, because the curated Inbox shows only that mail. A message already known stays quiet if it leaves the Inbox and returns within 30 days or is marked unread later, and unread mail dated more than three days before the previous look stays quiet when it enters the Inbox, as the main machine kept quiet about mail it already stored. A late alert names when the mail arrived. Mail that waits more than three days for its description does not alert. Foreground checks update that state and the badge without announcing. A background run posts one local alert for the new mail it finds after the refresh, naming the sender and description for a single message, then fetches descriptions for recent unread mail that has none and posts a second alert only for mail those descriptions make ready. Each alert is recorded in a private history file separate from calendar history.

With a Claude API key, Swift then calls `engine.backgroundDescribe`, provided no more than 8 seconds have passed, so the call's 16-second bound ends before the 25-second cut-off. Without a key it writes no descriptions. It does not send mail. Foreground mail reloads the description cache after background work finishes. The native build identity pins this host-only method; it is not added to the desktop RPC surface.

## Sender pictures and spending on the phone

The phone paints sender pictures with the same rules, prompts, limits and storage as the main machine (`src/inbox/pictures.rs`; [the Magpie guide](../MAGPIE.md#sender-pictures)), with three differences. It uses `gpt-image-2.5-flare`, which Dave chose for the iPhone and iPad in C-040, where Linux keeps Sunburst (Q-007); both are billed at the same token prices. It asks for one picture at a time. It sends a picture request only while the app is in the foreground, because iOS freezes the app soon after it leaves and a picture cut off there may still be charged. The check is made before each picture is reserved and again just before the request is sent, after the contact photo or logo has been fetched. `engine.suspend` waits for a picture under way until it is saved with its cost, within the same 8 seconds it waits for a description. A picture whose answer is lost after the app left (the app's departure count changed while it was under way) is cut off, not lost: it keeps its 7-cent reservation, because it may have been charged, but it counts no attempt and does not pause painting with `pictures_unreachable`, so ordinary app switching never gives a picture up. Every second cut-off of the same picture holds it back for 10 minutes, so short visits to the app go on to other pictures instead of asking for that one again and again. The app asks for painting only while Settings → Sender pictures shows pictures, and turning them off stops the run under way after the picture in hand. When an account is removed, the senders it alone had and their pictures are forgotten at once, with or without a key. The OpenAI key is an `OpenAiApiKey` credential in the device-only Keychain (`AfterFirstUnlockThisDeviceOnly`, not synchronised) and is sent only to api.openai.com. The phone asks for `contacts.readonly` and `contacts.other.readonly`, so contacts with photos get portraits as on Linux.

- `inbox.pictureStatus {}`, `inbox.setPictureKey {key}` and `inbox.removePictureKey {}` are the desktop's methods ([backend runtime](BACKEND-RUNTIME.md#sender-pictures-and-ai-spending-unreleased-api-8)); `inbox.snapshot` carries `pictures`, which changes when a picture is painted, and `inbox.avatar` returns `source: "painted"` for a painted sender.
- `engine.paintPictures {}` starts painting for the next signed-in Gmail account that is due and returns `{pictures}` at once, the number `inbox.snapshot` carries, so the app asks for the avatars on screen again when it changes. The inactive engine refuses it with `mobile_suspended`, and Swift calls it only in the foreground. Each account is looked at at most once a minute, as on Linux.
- `engine.stopPictures {}` stops painting after the picture in hand, because the app no longer shows sender pictures, and returns `{stopped: true}`; the next `engine.paintPictures` allows painting again. It takes no parameters.
- `engine.picturesToShare {limit}` (1–8) returns `{pictures}`: pictures painted on this device that iCloud does not have yet, each with `subject` (the 64-character picture id, the same on every device because it hashes the lower-cased account address and the sender), `kind`, `painted` (milliseconds), the JPEG in base64, and the photo `reference` and `photo` address when it is a portrait. The app saves each as a `SenderPicture` record named after its id in the `SenderPictures` zone of Dave's private iCloud database, then calls `engine.picturesShared {pictures:[{subject, painted}]}`, which records that iCloud has that painting (`{marked}`); a picture painted again is listed again.
- `engine.importPictures {pictures}` takes up to eight records from iCloud in the same shape and returns `{stored, kept, refused, pictures}`. A picture is stored, without cost, unless this device painted the same picture at the same time or later; it is then shown, never listed to share, and kept like a picture painted here, so an unused one goes after 30 days. Each record is checked as outside data: a valid id, a known kind matching any row already kept, a time no more than a day ahead, at most 2 MB of real JPEG no wider than 2048 pixels, a 64-character hex reference, an `https://` photo address only on a portrait, and no other fields. A record that fails is counted as refused and skipped. The app exchanges pictures before it asks for painting, at most once a minute and whenever Magpie comes to the foreground, and only in a build signed for the iCloud container.
- `ai.spending {day, week, month}` takes when today, this week and this month started in the phone's time zone, in milliseconds since 1970, each no later than now and at most 32 days back. It returns `{periods: {day|week|month: {descriptions, assistant, pictures}}, since}`, amounts in billionths of a dollar, and `since`, when the phone began counting (null before anything was counted). The engine keeps one total per feature and quarter hour for 62 days (`src/inbox/spending.rs`), and nothing about the mail. Amounts are estimates from the usage each provider reports at list prices: descriptions from each Haiku reply, Ask Magpie from each Sonnet reply, and pictures from each image reply's usage. An Ask Magpie request and a picture are counted at their reservation when they are sent and corrected to their cost, in the quarter hour they were sent, when the answer comes; one lost after it may have been charged, or ended with the app, stays counted at its reservation, as the daily limits count it. Open reservations are kept for a day, at most 64, by an opaque request id; a request whose open reservation was dropped (older than a day, or ahead of a clock that went back) or already settled stays counted at its reservation rather than counted again. They are not the providers' bills.

## Descriptions written on the phone

A phone that holds Dave's own Claude API key writes Inbox descriptions itself with the same rules, validation and storage as the main machine (`src/inbox/describe.rs`). `src/inbox/claude.rs` calls `POST https://api.anthropic.com/v1/messages` with `claude-haiku-5-5`, low effort and no tools, through a client with no proxy, no redirects, HTTPS only and bounded replies. The key is a `ClaudeApiKey` credential in the device-only Keychain (`AfterFirstUnlockThisDeviceOnly`, not synchronised). It is read from the Keychain for each batch of messages and each status check, sent only in a sensitive `x-api-key` header, and never returned, logged or stored elsewhere. Only Console API keys are accepted: personal (`sk-ant-usr…`), service account (`sk-ant-svc…`) and older (`sk-ant-api…`) keys; the two newer prefixes come from third-party reports, since Anthropic documents only the `sk-ant-` start. A key not scoped to one workspace is refused with `ai_key_workspace`, because every request would need an `anthropic-workspace-id` the phone does not hold.

- `ai.setKey {key}` checks the key with `GET /v1/models/claude-haiku-5-5` before saving it and refuses a malformed key before any request. `ai.removeKey {}` deletes it. `ai.keyStatus {}` returns `{present, model, problem}` and never the key.
- `engine.overviews` and `engine.overviewSettings` take the parameters and return the shapes that the main machine's former `/v1/overviews` and `/v1/overview-settings` used, so descriptions the main machine wrote earlier read the same way. A request names at most 100 ids to read and at most 4 to describe. A page returns the stored descriptions for those ids only. Rows also carry `attempts`.
- `engine.backgroundDescribe {accounts:[{accountId, ids}]}` runs only while the host is inactive. The app names at most 20 unread Inbox messages per account that have no saved description, so mail the main machine already described is not described again. The engine describes the first 4 of them that are due, so messages that failed or are still being described do not hold back the ones behind them unless nearly all 20 are in that state. It starts no further account once fewer than 3 of its 14 seconds remain, and the host bounds the call to 16 seconds. A description still being written when the call returns is saved only if iOS keeps the app awake long enough; otherwise the message is asked about again later.

Cost and failure rules:

- Each message is read, prepared and described on its own, so a message that cannot be read, prepared or described fails alone. A message takes one to three free token counts and two or three passes (the third only when the second answer fails validation), and its passes start again without its PDF if Claude refuses the PDF. Its media comes first with a cache point and the instructions last, so the second and third passes read the media from the prompt cache.
- Before a message is sent, `POST /v1/messages/count_tokens` counts it without charge. PDFs, then pictures, are dropped until it fits within 80,000 tokens, and a message too long without them fails. Recipient and attachment lists are cut to 50 entries each. With the rules and the earlier passes' answers added, a request stays below Haiku 5.5's 100,000-token price step. The phone cannot render PDF pages, so it sends a PDF as a document block; if Claude refuses a PDF, the message is described without it.
- Spending is counted from the token usage Claude reports and stops for the day at about $0.50, or after 1,500 calls including counts. The day follows UTC. A request cut off when iOS suspends the app may still be billed without being counted, so the spend limit on the key's workspace in the Claude Console remains the firm limit.
- Each request to Claude that fails for a reason that says nothing about it (a lost connection, a timeout, 408, 409, 429, a 5xx including 529, or `x-should-retry: true`) is sent again up to three times, after about 1, 2 and 4 seconds, or after the wait in `retry-after-ms` or `retry-after` when that is at most 30 seconds, and only within 90 seconds of the first attempt; time the app spent suspended does not count towards the 90 seconds, and a request that failed while the app left the foreground is not sent again until it returns. Every attempt is counted against the day's calls. A request that still fails, or a wait Claude asks for that is longer than 30 seconds, starts the shared backoff: 15 seconds, doubling after each further failure to at most five minutes, or Claude's wait when that is longer (at most an hour). The first description Claude writes ends the backoff; a successful token count does not. A connection lost while iOS suspended the app starts no backoff, and the message is asked again when the app returns. A failure of Claude or the key stops the batch; the messages after it are returned as not asked (`stage: "batch"`).
- A missing, refused or invalid key, a billing problem, the shared backoff or the daily limit refuses before any message is claimed: `engine.overviews` then answers `accepted: false` with `problem`, and the app stops asking but keeps reading pages. An invalid or refused key stops requests until Dave replaces it; billing waits an hour. A failure from a request made with a key that has since been replaced is ignored. The app reports only problems Dave can act on or that last the day (key, model, billing, daily limit). A lost connection, rate limit or unavailable service is reported only after Dave presses Retry, or once descriptions have waited for it for 15 minutes, when the Inbox and AI descriptions say so.
- On the phone a message that could not be described for Claude's or the mail's reasons is `waiting`, not `failed`, and keeps its attempts. One that was not asked because Claude or the key failed first, or because the app left, carries no `retryAt` and is asked as soon as the shared backoff allows. One whose own request failed for Claude's reasons carries `retryAt` one minute later, doubling to 15 minutes, so the messages it held up go first; one waiting after a Gmail or storage failure carries `retryAt` 15 seconds later, doubling to 15 minutes (`waits` counts both). A message whose own description failed, or whose mail could not be prepared for its own reasons, is `failed` with `retryAt` one minute after the first failure and five after the second; after the third it has no `retryAt` and is not asked again automatically. Retry in Settings forgives every failed message in every account and makes every failed or waiting message due at once. A row still `running` from before the engine started, left by an app iOS ended, is reported as `waiting` and asked again at once. The main machine and Magpie on Linux keep `failed` and their 15-minute retry. Known limit: a message for which Claude keeps answering with a server error or a rate limit counts as a service failure each time, so it is never capped; it is asked again at most every 15 minutes.
- When the app leaves the foreground, the batch stops after the message under way and the rest are returned as not asked (`overview_interrupted`); a batch whose mail was still being prepared sends nothing. `engine.suspend` first waits up to 8 seconds for the message under way, or until the app returns, then writes the diagnostics below. A background describing run writes them when it ends.
- The engine keeps `omamail/diagnostics/claude.json` in the private state directory: at most 1,000 events and 256 KiB. An event is one HTTP attempt (operation `count`, `describe`, `assistant`, `keyCheck` or `workspaceProbe`, attempt number, status or failure class, Claude's retry wait, the wait chosen, duration and a fixed outcome code), a backoff (level and wait), a batch (how many were described, waiting or failed), a background describing run, the app leaving or returning to the foreground, or how long leaving waited. Each event says whether the app was in the foreground and whether it left during the work. Every field is checked against a fixed list or bound before it is written; no message id, address, mail text, header, key or server text is recorded. Settings → Share diagnostics… exports this file and `gmail.json` with the app version and counts of description states; `scripts/diagnostics.sh` in magpie-ios prints them as a timeline from the paired iPhone.
- When the phone writer has no saved settings for an account, and whenever a key is saved, the app sends this iPhone's pause and remote-image settings first. These settings stay on the iPhone; Magpie on Linux keeps its own.

Model output stays untrusted: descriptions pass the same validation as the main machine's and cannot route, send or change mail.

## Questions answered on the phone

A phone that holds Dave's Claude API key answers Ask Magpie itself (`src/inbox/assistant.rs`). It uses the same key, client and request limits as descriptions, with `claude-sonnet-5-5`, low effort, the desktop assistant's rules (`src/agent/prompt.rs`) and its single `propose_draft` tool. The calls keep the shapes of the `/v1/ai/*` calls that the main machine served before Magpie for iPhone 0.1.32. Without a key, the phone asks nothing and shows where to add one; conversations asked on the main machine before 0.1.32 do not move to the phone.

- `ai.start {accountId, messageIds | draft, prompt, requestId, issuedAt, parentId?, events?}` checks the question, reads the named mail into a context as the desktop's `agent.context` does, saves the job and returns it at once. The turn runs in its own task, never inside the call. A retry with the same account and `requestId` gets its job back, even during a key problem; a different question under it is refused. A non-empty `provider` or `model` is refused, because the phone always uses Claude Sonnet 5.5.
- `ai.show {id | accountId and requestId, before?}` returns `{job, output, transcript, proposals, previous}` with up to eight turns of the conversation. `ai.list {offset?}` returns 32 jobs at a time, newest first. `ai.cancel` stops a turn once the cancellation is saved, so a cancellation that cannot be saved fails and leaves the turn running; a question cancelled by its request before it arrives is refused when it does. Removing an account likewise stops its turns only once its questions are gone from the index.
- A follow-up replays the history Claude has already seen exactly, thinking included, and adds only what changed. A history kept under other rules or another model, one over 1 MiB, or one Claude could not take (`ai_request_rejected`, `ai_context_full`, `agent_context_too_large`) is supplied again as text instead, so a long conversation does not fail the same way on every follow-up.
- A turn makes at most 8 requests. A proposal holds only a subject and a body; its account, message and draft come from the job, and Dave applies it in the editor and sends it himself. Nothing in the assistant edits, sends or moves mail.
- Spending is counted apart from descriptions: about $2 a day (Dave's choice in Q-005) or 400 requests, by UTC day. Each request reserves the most it could cost before it is sent and is settled to the usage Claude reports. After the day's first request, a request whose reservation does not fit what is left is refused with `ai_daily_limit`, so long conversations, whose reservations are large, reach the limit before $2 of actual use. A request cut off by a lost connection keeps its reservation. Each counted request stays open in the ledger until it is settled, so a retried write counts or settles it once; a request still open at midnight counts on the new day, and one open for 15 minutes is dropped with its reservation still counted.
- Only an invalid key, a key a mail-free probe confirmed is not tied to one workspace, and a billing pause are shared with descriptions. A refusal, rate limit, unavailable model or lost connection stays on the question.
- Questions and answers are kept in the private inbox store: at most 200 questions and 256 MiB, the oldest finished ones removed first. Entries read back are checked against what the engine writes, and anything else is dropped or refused. Removing an account removes its questions and stops their turns. A record whose removal fails is listed in the index and removed on a later question or account removal. A queued or running turn with no task, because the engine stopped, reads as `ai_interrupted` and can be asked again.
- The assistant's index, records and ledger change under their own lock (`.assistant-lock`), not the inbox's `.lock`, so a long assistant write never holds up descriptions, snoozes or overviews, which still fail at once when their lock is busy. Assistant writers wait up to 2 seconds for each other, on blocking threads, never on the engine's request thread or a runtime worker. A turn's store changes are tried again three times, 500 ms apart, when the store is busy; a change that still cannot be made fails the turn with the store's error, except a settlement, which leaves the request's reservation counted. Readers that do not take the lock (show, list and a repeated start) treat a queued or running question as interrupted only when its task has ended and a second read still shows it active, so a turn that finishes while it is being read shows its answer.
- A follow-up's history is gathered before the index lock is taken; under the lock the engine only checks that the parent is unchanged, and gathers it again in the rare case that it changed.

Apple documents discretionary scheduling in [background task guidance](https://developer.apple.com/documentation/backgroundtasks/refreshing-and-maintaining-your-app-using-background-tasks). Simulator checks cannot establish physical-device delivery, scheduling frequency or operation before the first device unlock.
