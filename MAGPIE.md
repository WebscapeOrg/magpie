# ✉️ Magpie Mail

Magpie Mail, called Magpie until 8 November 2026 (Dave, C-065), is Dave's MIT-licensed fork of [Omamail](https://github.com/huacnlee/omamail). It uses Omarchy's theme with proportional fonts and offers a single-pane reading flow alongside the original split view. The name people see is Magpie Mail and its icon is Apple's ✉️. The repository (`WebscapeOrg/magpie-mail`), plugin id `magpie-mail`, `magpie-mail-engine.service` and the iPhone install address (`/installs/magpie-mail/`) carry the new name too (Dave, Q-017). Kept on purpose, so that sign-ins, links and saved mail carry on: the iPhone bundle id `net.anotherdave.magpie`, `magpie://` links, the engine binary and data folders named `omamail`, keyring entries, Gmail's hidden `Magpie-snooze-…` labels and the `# Managed by Magpie` marker on units. The rest of these docs say Magpie for short.

Open a message with a click or Enter. **Back**, Escape, or Left returns to the list. **Menu → Split view / Single pane** changes layouts. The first launch uses single pane; the choice is saved.

Open **Settings → Layout and fonts** with **Ctrl+,**. Interface, message list, and message body each have their own font chooser, size in points, and preview. Settings save automatically. Initial values are **Chillax Light, 17 pt** in all three regions. Choose **System UI font** to follow the desktop's proportional `sans-serif` fontconfig alias. This does not change Omarchy's bar or terminal fonts. An inherited Omamail message zoom is reset to 100% when Magpie first creates its font preferences. Later zoom choices are retained. Message zoom remains available with Ctrl++ / Ctrl+- / Ctrl+0 on top of the configured message size. Original-format messages may retain their sender's explicit styling; Reading and Plain text use your message font.

## Inbox

The Inbox groups messages waiting for their [Point](#the-point) into one current-message card above the readable mail. It shows one card for one waiting message, two cards for two, and three cards for three or more. The card represents a message in the live working batch when one is in view, otherwise the next waiting message. Its sender and time stay visible, and a moving highlight crosses two lines where the Point will go. Completed Points join the readable list in date order; a line above the list says how many messages Magpie is working through. A message whose own attempt failed shows its subject and preview, with no warning, and is asked again later. Only a lasting problem gets one line, with its fix beside it: paused (Resume), every Claude subscription used up for now, or Claude not answering for 15 minutes while the window is open (C-051). The phone keeps the lines still under Reduce Motion. The desktop has no system reduced-motion setting. Selecting messages reveals the waiting rows so a selection never becomes hidden. Search, All mail, original subjects and a lasting hold show ordinary rows. Choosing original subjects shows subjects and previews with no lines. Notifications still wait for the Point. The main machine prepares downloaded Inbox mail even when the window is closed.

Unread Points use an earthy marker stroke and regular text. Each row has a circular sender avatar: a painted sender picture, an available Google contact photo, an organization logo cached by sender domain, or one initial. The **All / house / tree** account selector switches accounts or opens the unified inbox; Personal uses a house and Webscape uses a tree. Message rows show the date without mailbox symbols. **Folder** shows or hides folder navigation; it starts hidden. Layout, refresh and AI tools live in the main menu. The monochrome bird is shared by the window and bar.

Hover a row or move to it with the keyboard for **Mark unread**, **Snooze**, **Archive**, and **Trash**. Snooze offers tomorrow, the next Saturday and the next Monday at 08:00 in the local timezone, plus a custom future date and time. It saves the schedule, then archives the conversation and gives it a hidden Gmail label named for its wake time, rounded up to five minutes (for example `Magpie-snooze-2026-11-02-0800-UTC`), in one Gmail change. Because the schedule lives in Gmail, any Magpie signed in to the account, on Linux or on the iPhone, lists the snooze and returns it when it is due, whichever runs first. The persistent shell service checks every 30 seconds, returns due messages to Inbox as unread, catches up after resume, and leaves later Trash or Spam moves intact. A snooze made while Gmail cannot be reached, or does not answer within 25 seconds, is saved and finished on a later check; it then snoozes only the mail that had arrived when you chose it, and it gives way if you snoozed or returned the conversation on another device in the meantime. A snooze Gmail keeps refusing is tried again after a growing pause, so it never holds up the others. **Menu → Snoozed mail…** returns a conversation early. Deleting a snooze label before its time, for example in Gmail's settings, does not end the snooze: a Magpie that is running labels the conversation again, and one that was off until the time passed still returns it, provided it runs within three days of that time. Moving a snoozed conversation to Trash or Spam ends its snooze. The labels are hidden from Gmail's label list and message chips and from Magpie's own folder and label lists, although an IMAP client may still show them as folders. A snooze label is deleted three days after its time, once no mail carries it. Snoozes saved before this version get their label on the next check, so the other devices see them too.

[The Point](#the-point) replaces the list subject and preview, and the row grows to show all of it. The row keeps that height when its tools appear on hover or under the keyboard cursor: the Point is cut to the lines it already has, and hovering the text of a cut Point shows it whole. The original subject remains in the reader and is shown in the list while a Point is missing, expired or unavailable. **Menu → Show original subjects** turns Points off; **Show the Point** restores them. **Pause new Points** stops new work after the admitted batch, and **Retry Points** retries failures. Points are reading aids and can be wrong.

A picker first chooses the Claude model for each email (see **Which model** below). Haiku drafts each Point and a separate editing pass checks it against the mail and its context; Sonnet and Opus write it in one pass. Any answer the checks refuse is repaired once. On the main machine every run first goes through `claude-routed --claude-only`, which places it on one of the Claude subscriptions (P, W, S or H) as agent sessions are placed and never on GLM; pictures and PDFs go to Claude with the email. When all four Claude subscriptions are out for that model the router exits 75, and Magpie consults the main machine's subscription switcher (`reincarnate status --json`) to fall back across the Codex subscriptions (P and W, using GPT-6 Luna, GPT-6.1 Sol and GPT-6 Astra) and then the Google AI subscription (`agy`, using Gemini 3.8 Flash and Gemini 4 Argon) (C-060). Only when every subscription across all three providers is out does the email wait as paused (`overview_ai_paused`), where it is not counted against itself and is tried again after 15 minutes. A router without the Claude-only mode, or one whose probe does not answer, gets nothing: the email waits the same way and nothing goes to GLM. Z.ai's vision model is no longer used. Without the main machine's router the Claude CLI runs directly. No model has tools or authority to send mail. Mail, pictures and attachment content supplied for Points leave the main machine for Anthropic, OpenAI or Google according to the active subscription; this app makes no claim about provider retention.

Context is bounded: at most 16 files and 2 MiB of source media per message, 48,000 body characters and 96,000 attachment-text characters. Raster images are downscaled to at most 1568 pixels and transparency is composited onto white. PDFs supply text from at most 100 pages and pictures of the first two and last two pages. Office documents supply text, tables and up to eight embedded raster images. Unsupported, encrypted, oversized or failed files are marked as unavailable; omitted content is never presented to the model as read. Linux document parsing runs in the existing network-free filesystem sandbox. Remote pictures follow the reader’s opt-in preference and the checked public HTTP boundary; links are not opened. Versioned results are cached by account/message. A Point expires when the model says it stops being true, at midnight when it uses words such as today or tomorrow, and six days on when it names a weekday, counted from the date supplied to the model even if generation finishes later. Exact text evidence and output shape are checked in code; visual grounding is a model/editor check, not a proof that the Point is true.

Google sign-in requests optional read-only Contacts access for contact photos. After granting it, choose **Menu → Refresh sender images** to refresh cached photos and logos immediately. If that access is unavailable, the row still uses the organization logo or initial. Avatar fetches use the backend's checked public HTTP transport and return raster data to Qt; the UI never loads sender-supplied remote URLs. Caches and this device's copy of the snooze schedule live in private files below the platform state directory's `omamail/inbox/`.

### Sender pictures

With an OpenAI API key in **Settings → Sender pictures**, the main machine's mail engine paints a picture for every sender who appears in an Inbox, in the ligne-claire style Marmalade uses for its X avatars. It uses OpenAI's gpt-image-2.6 Sunburst at medium quality, 1024 pixels square, and Marmalade's prompts word for word, with one added sentence asking for the subject to fit inside a circle. A sender with a Google contact photo is redrawn from that photo as a portrait; a sender at a company is drawn from the company's logo or favicon as a logo plate, shared by everyone at that company's registrable domain, so `news.acme.co.uk` and `acme.co.uk` share one picture (names under a hosting domain such as `github.io` share the host's picture); any other sender, such as a Gmail address with no contact photo, gets the first letter of their name drawn as a monogram, so no face is invented. Only the contact photo or logo and the fixed prompt leave Magpie; the prompt contains at most the company's domain or one letter, never a name, address, subject or message text. Each picture is painted once and kept as a private 512-pixel JPEG below `omamail/pictures/`; it is cut to the circle when shown, so it fills the avatar edge to edge. When a contact's photo changes, the new photo is compared with the one already painted and is painted again only if its pixels differ; until then the current picture stays. Pictures appear in the window within seconds of being painted.

The engine looks at each signed-in account's Inbox once a minute, paints portraits first and at most two pictures at a time. Spending is an estimate from OpenAI's reported token usage at gpt-image-2.6 Sunburst's list prices ($5 per million text input tokens, $8 per million image input tokens, $30 per million image output tokens), not OpenAI's bill. Painting stops for the day once the estimate reaches $3.00. Test pictures on 2 November 2026 cost 1.4 cents for a monogram and 2.3 cents for a logo or a portrait; Settings rounds each picture up to a whole cent, and each request holds 7 cents of the limit until OpenAI reports what it used. A picture OpenAI refuses, for example by its safety system, is asked for again an hour and then six hours later, because such a refusal does not always repeat, and is then given up: Settings counts a new picture given up this way as one that could not be painted, and its sender keeps their usual picture, while a portrait whose contact photo changed keeps its current painted picture. If OpenAI instead rejects a setting that every request shares, such as the model, size or quality, the picture is asked for again a day later, and three such rejections in a row stop painting for a day. A picture whose request is lost is tried at most three times, an hour and then six hours apart. A refused key stops painting until a new key is saved; a billing or rate-limit refusal pauses it for an hour or a minute. Saving or removing the key stops a run that is still using the old key from sending more requests; at most two requests already sent finish and are paid for. While the contacts cannot be read, senders keep the portraits they have. A picture no sender uses any more is kept for 30 days in case it is needed again, and a sender who has not been among an Inbox's newest 2,000 senders for 90 days is forgotten. When an account is removed from Magpie, the next painting run forgets its senders and deletes the pictures and prepared copies no other account uses. Signing out keeps them, so signing in again does not pay for them again. The key is checked with OpenAI before it is saved in the system keyring and is never shown again.

Magpie on the iPhone and iPad paints pictures the same way with its own OpenAI key, saved in **Settings → Sender pictures** on each device, using gpt-image-2.6 Sunburst as Linux does; it used Flare until Dave moved it to Sunburst on 3 November 2026, because Linux's pictures looked better. From version 0.1.39 the device that painted a picture with Flare paints it once more with Sunburst, after every new sender's picture and within the same daily limit, and shares the new one; the Flare picture shows until then. Dave chose this on 4 November 2026 (about 2 cents a picture). A picture that cannot be painted again keeps its Flare picture. Each device paints one picture at a time, only while Magpie is open on screen and Show sender pictures is on, and has its own $3.00 daily limit; switching away from Magpie while a picture is under way does not count against that picture. A picture painted on the iPhone reaches the iPad through Dave's private iCloud, and the other way round, so a picture is usually painted, and paid for, once: a device takes in what the others painted before it paints, but two devices can both paint a new sender before either has shared it. A device without a key still shows the pictures the others painted. The copies in iCloud are kept when an account is removed or a picture goes unused on one device, because another device may still show them. **Settings → AI spending** on the phone shows the estimated spending on that device on descriptions, Ask Magpie and sender pictures today, this week and this month. Magpie on Linux has the same section in Settings, below Sender pictures, for the pictures painted on the main machine; its descriptions and Ask Magpie use the agent chosen under AI rather than Magpie's own key, so they are not counted there. See [the mobile engine](docs/MOBILE-ENGINE.md#sender-pictures-and-spending-on-the-phone).

## The Point

Press and hold a message on the phone, or open its menu on the main machine, and choose **Point details**. **Downloaded during** and **Analysed during** record the two steps separately: background refresh, using Magpie, or the main machine. If you leave or reopen the phone app during a step, the details say so. Background work that continues after you reopen Magpie keeps its background origin and says the app was already open. **Context tokens sent** shows the input tokens reported across the writing passes, including reused context. **At least** marks a lower bound when a request did not report usage. **Models and effort** names each model that wrote the Point with the effort it was asked for, and GPT-6 Luna when it chose the model. **Estimated API cost** is what those requests and the model choice cost at each provider's API list price, or would have cost for a Point the main machine wrote with a subscription; the prices and their sources are in `src/inbox/prices.rs`. The main machine labels shared batch totals. Older mail says **Not recorded** where the app has no history. Cached reads keep the original record; a later fetch of missing body text is labelled **remaining text**. Failed rewrites keep the details of the Point still displayed.

Dave's product vision (4 November 2026), word for word:

> 🐦 Magpie Mail
>
> Traditional email feels overwhelming because it bombards you with information that doesn’t matter. Subject lines are more miss than hit. The first few lines of text are usually just noise.
>
> Your inbox can—and should—be much smarter. It should hide everything that isn’t helpful and, for each message, answer one simple question:
>
> What’s the point?
>
> Magpie answers that question in one short line. We call it The Point.
>
> It reads each email and its attachments in the context of your life: who you are, your calendar, your to-dos, your other conversations and what you’ve already dealt with. It works out what the message means for you, right now.
>
> So your inbox looks like this:
>
> John · 15m ago
> He wants to know if tonight’s dinner is still on.
>
> Netflix · Yesterday
> Price rise starts after your subscription ends. No action.
>
> Sarah · 25m ago
> You already sent this to her colleague yesterday.
>
> Sometimes the point is that someone needs an answer. Sometimes it’s that a change won’t affect you. Sometimes it’s that you’ve already handled it.
>
> Magpie connects the dots, saving you the work of remembering, searching and checking.
>
> Magpie. An inbox that gets to the point.

Getting the point across comes first and brevity second. Most Points fit on one line (the rules aim for 50 to 100 characters); a dense or complicated email may get up to three short sentences, never more than 300 characters (`POINT_LIMIT` in `src/inbox/mod.rs`, `ui/inbox/Readiness.js` and the iPhone's `MailDescription.limit`). Points address the owner as you and do not use their name, and they never guess anyone's gender: people are named or called they, and the engine refuses a he, she or her that neither the email, its thread nor the bio uses. Dave's own example "He wants to know if tonight's dinner is still on" is therefore written "John wants to know…" unless John's mail says he.

**What it reads.** With each email the model gets, as data and never as instructions: the owner's own description of themselves from Settings → About you (at most 2,000 characters); the last 14 days of sent mail and the other Inbox mail from every account on the device (40 each: sender, recipients, date, subject and first 300 characters); the earlier messages of the email's thread (six, 4,000 characters each); and recent mail with the same sender (six from the last 60 days). All of it is read from the local copy of the mail, never fetched from Gmail for this. With it comes the calendar, from a week back to a month ahead (at most 120 events, nearest to now first): each event's title, start and end, place, organizer, up to ten attendees and the owner's answer, each cut to 200 characters, and never its description. With them come the owner's todos: the open ones (at most 60) and those done in the last two weeks (at most 40, most recent first), each with its title, status, list, start and deadline days, when it was done, which side it is on and the email it came from; never a todo's notes. The shared part comes first so the phone's requests can cache it.

**Calendar.** Magpie reads Google Calendar itself, with the read-only `calendar.readonly` permission, and never changes it; Magpie Calendar still owns calendars. Each account's primary calendar and up to nine others the owner shows are read at most every ten minutes (`src/inbox/calendar.rs`), and an event in several accounts or calendars counts once (by its iCalendar UID). Settings → Calendar shows whether each account's calendar is read (`inbox.calendarAccess`); Allow signs the account in again so Google adds the permission, and then reads that calendar at once. A sign-in made before this version has not granted it, so the calendar is not read until Allow is used; a new sign-in asks for it with the other permissions, and leaving it unticked still signs in. A failed read keeps the last good one for up to a day; a Google project with the Calendar API switched off counts as a failed read, since signing in again cannot fix it. On the iPhone, Read Apple Calendar passes Apple Calendar's events in the same form (`engine.appleCalendar`), counted for a day; the iPhone's short background run uses only what was read before and never waits for Google.

**Todos.** The Point reads Atlas's Magpie feed (`GET https://atlas.anotherdave.net/api/v1/magpie/todos`) with a key that reads that feed and nothing else (`src/inbox/todos.rs`). Dave connects each device once: in Atlas, Settings → Connections → Magpie makes a key and shows a `magpie://connect` link; the iPhone opens it, and on the main machine it is pasted into Settings → Todos (`inbox.todoConnection`). Magpie accepts a link only for that address, keeps the key in the device's keyring or Keychain, and never shows or logs it; Disconnect removes it and the todos read with it. The feed is read at most every ten minutes, a failed read keeps the last good one for up to a day, a refused key asks for a new link, and the iPhone's short background run uses only what was read before. A binned todo is left out, since it does not show that anything was handled. On the iPhone, Read Apple Reminders passes Apple Reminders in the same form (`engine.appleReminders`), counted for a day. Moving to Magpie To Do's own server changes only the address and the key.

**Evidence.** Every fact a Point takes from the email or its context quotes where it came from (`mail`, `file:N`, `thread:ID`, `related:ID`, `sent:ID`, `inbox:ID`, `todo:ID`, `event:ID` or `bio`); a field of a context entry, such as a to-do's status, may be quoted with its exact value (`"status":"done"`); the first quote always comes from the email itself, and the engine checks each quote against the text it sent. A Point that fails is repaired once and otherwise not shown. Each stored Point keeps its source tags, not the quotes.

**About you.** Settings → About you holds the owner's own text, edited in place (`inbox.aboutYou`). On the main machine it is kept in the engine's private state. On the iPhone and iPad it is kept in each engine's private state and shared between the two as one record in the owner's private iCloud database, with the text end-to-end encrypted; the latest edit wins. It is never logged or put in diagnostics. It refuses markup brackets, control and invisible characters.

**Which model.** OpenAI's Decisions API (`gpt-6-luna`, `src/inbox/picker.rs`) answers one choice question per email with the owner's OpenAI key, the one Settings → Sender pictures holds: Haiku 5.5 for automated mail (newsletters, receipts, order and delivery confirmations, sign-in codes), Sonnet 5.5 for mail from a person or mail that needs the owner to act, answer or decide, and Opus 5.5 for health, legal and similar high-stakes mail. When unsure it leans upward: Opus when Opus is at least 25% likely, otherwise Sonnet when Sonnet and Opus together are at least 35%, otherwise Haiku. No key, an error, a refusal or no answer within 10 seconds means Sonnet, so a Point never waits on the picker. Each stored Point records its model (`tier`). The picker's cost ($0.10 a million input tokens) is counted on the spending page and, on the phone, in the daily limit. The phone's short background run writes only Haiku Points; Sonnet and Opus Points are written when Magpie is next open. A key or workspace that cannot use Sonnet or Opus gets that Point from Haiku instead, and that refusal pauses nothing else.

**What leaves each device.** Anthropic receives the email and the context above. On the main machine that happens only through the router's Claude-only mode; without it nothing is sent. OpenAI receives, for the picker only, the sender's name and address, whether the owner has written to them, up to five of Gmail's category labels, whether the email offers to unsubscribe, the subject, its first 600 characters and up to 20 attachment names, each name, address, label and subject cut to 200 characters; never the bio, the calendar, the todos, the attachments' contents or any other mail. Google is asked only for the calendar and Atlas only for the todos; nothing about the mail is sent to either. A question or answer over 64 KiB is never sent or read, and on the main machine the picker is asked only when the router's Claude-only mode means the Point will be written. The Decisions guide describes no setting to keep requests from being stored, so OpenAI's normal data controls apply. Z.ai receives nothing.

**Writing Points again.** A Point written under earlier rules stays in view and is written again (`POINT_REVISION`); the iPhone is told with `refresh`. A Point written from the email alone, before the router had its Claude-only mode, is written again once the mode is there. A Point still in the Inbox is also written again when the owner has since sent mail in its thread, or when an Atlas todo linked to it (by the email's thread or Gmail id) was done, reopened, added or removed (`src/inbox/rewrites.rs`). Each Point keeps a key of what it was written against, which holds only hashes, and the engine compares it with the present at most once a minute per account, on the main machine's tick and when the iPhone asks for a page. Nothing else counts, so the cost stays bounded: other todos, the calendar and other mail never have a Point written again, and todos that cannot be read (not connected, or not read for a day) are never a change. The old Point stays in view until the new one is ready. A Point also stops showing when its `until` passes, and Retry asks again at once.

**Bundles.** When a new mail makes an earlier Inbox mail need no separate attention, the earlier one moves behind it: one row, one Point, a count (Dave, Q-019 and Q-020, C-073). The writer of the Point names such mail with a short exact quote, up to five per mail, and the Point of each mail shown travels with the request after its cached part, so the shared cached part does not change. Every check that decides it is the engine's (`src/inbox/bundles.rs`, `src/inbox/sender_proof.rs`): same account, shown to the writer, older by Gmail's date, with a Point of its own written under today's rules, and a sender Gmail proved (`Authentication-Results` from `mx.google.com` with a domain-aligned DMARC or DKIM pass). Mail of one proven sender bundles by itself; a different sender in front waits for a one-tap approval, which approves that sender on this device (Settings lists and removes them). Never hidden: starred mail, drafts, mail sent by the owner or from their other accounts, attachments, calendar invitations, mail linked to a todo, a Point with an end date still ahead (the writer's `until`, saved as `untilAt`, separate from `expiresAt`), mail with an unsent reply draft, and mail snooze brought back (the hidden Gmail label `Magpie-snooze-returned`, added in the same change as the wake, and kept out of label lists). A writer that is not Claude makes no bundles. Each older mail has one front, the newest to claim it; a chain of follow-ups becomes one bundle; "Not the same Point" is remembered on the older mail alone. If the front leaves the Inbox the older mail comes back and its Point is written again. A sender's older mail is written before the newer one, because a cover needs its stored Point.

On the main machine, in the Inbox only, a bundle shows as one row: the newest mail's sender, time and Point with a small count after the name, and the row reads unread if any mail in it is unread. A proposal keeps both rows and the newer one offers **Bundle these?** with **Bundle** and **Dismiss** (`ui/inbox/Bundles.js`, `ui/inbox/BundleBook.qml`). Opening a bundled row marks every mail in it read and the reader lists the others under **Also in this Point**, by sender, time and subject. **Not the same Point** in the row's menu brings the older mail back. Archive, Trash, Snooze and Mark read/unread on a bundled row reach every mail in it, through the same batch path as a selection; a selection reaches every mail of each bundled row in it. Report spam and Move to label stay on the mail they were pressed on, since Q-020 decided only the actions Undo can restore, and the older mail then comes back as its own row. After Archive, Trash or Snooze, a toast says **Archived 2 messages** with **Undo** (or Alt+Z): Undo drops an Archive or Trash still queued to sync and reverses one Gmail already has, restoring only what that change altered; Snooze is undone by returning the mail as it was, not unread and not marked as returned. **Settings → Approved senders** lists and removes approved senders. If the engine lacks these methods, or its answer fails three times running, the Inbox shows one row per mail as before and failures go to the log, never the main screen. While the first answer is on its way the list waits, up to a moment and a half, so no row visibly jumps.

**Eval set.** `tests/point-eval/` holds about thirty synthetic emails read against a synthetic owner (`base.json`), each with the point a person would want, words it must and must not use, and the sources it should draw on: Dave's three examples, health, legal, automated mail, mail from people, mail already handled, and instructions planted in another email, a to-do and a calendar entry. `cargo test --lib inbox::point_eval` checks offline that every hand-written answer passes the engine's checks. `cargo test --features integration-test-credentials --lib -- agent::overview::live_quality::point_eval --ignored --nocapture` writes every case live on the main machine's Claude-only route, grades each Point with Claude against its expected point, and writes the results to `POINT_EVAL_OUT` (`POINT_EVAL_ONLY=id,id` picks cases, `POINT_EVAL_TRACE=1` prints each pass's answer). Each case is written with the model the picker chooses, asked of OpenAI itself with the OpenAI key saved in Sender pictures (ordinary tests can never reach OpenAI), or with `POINT_EVAL_TIER=haiku|sonnet|opus` for all of them, and the summary counts how often the picker chose each model and how often it matched the case's kind (automated, person, high-stakes). It fails when context could not be sent, when fewer than nine in ten cases get a Point, when the picker answered fewer than nine in ten cases (a picker that is never reached chooses Sonnet for every case, which looks like a choice), or when a Point says a word its case forbids.

**Magpie interviews you.** In Settings → About you, choose **Magpie interviews you...** to answer six optional questions about your life. The first question stays on the device; after consent, Claude Sonnet receives only the current bio and the questions and answers supplied in this interview. No mail, calendars or todos are included. Skip any question or ask for a draft early. Review and edit the draft, then choose **Save bio**; cancelling keeps the saved bio. The iPhone also offers on-device dictation. On the main machine the interview uses the Claude-only subscription router; on the phone it shares Ask Magpie's daily spending limit. A device with Points enabled and no bio offers the interview once (the phone also waits for iCloud and needs a Claude key). The saved bio can still be edited directly.

**Decisions (C-050, 4 November 2026).** Dave chose: Claude subscriptions only on the main machine, switching between P, W, S and H and pausing only when all four are out; the whole Point shown, with the row growing; Points written again when something related changes; the OpenAI Decisions API choosing Haiku, Sonnet or Opus for each email; about $5 a day on the phone (up from about $0.50); the bio kept on each device and shared between iPhone and iPad through iCloud; Google Calendar read by Magpie itself, read-only, with Apple Calendar as an iPhone option. Stage 1 covered the rules, evidence, 300 characters, rows that grow, About you, sent and Inbox mail as context and the phone's limit. Stage 2 added the picker and the three models, and ended Z.ai's part in Points. Stage 3 added the calendar. To-dos, rewrites on related changes and the "Magpie interviews you" onboarding follow in that order. This reverses the earlier 5–10-word target (C-020, C-031) and the estimate of about $1 a month for descriptions in settled questions.

## Installation on the main machine

The maintained checkout is the main one, not a worktree. The main machine's `omarchy/install.sh` copies its runtime files into the `magpie` plugin and `script/omarchy-selfheal` verifies those copies. There are no development symlinks. The installer checks the session lock before every watched write and never restarts Quickshell. See the main machine's living machine map for the migration and account setup.

Install the supplied font archive locally with `python3 scripts/install-font.py /path/to/Chillax_Complete.zip`. The font and its Fontshare license stay in the user's font directory; they are not redistributed in this repository. The UI loads the installed face through FontLoader, so it does not need a shell restart to recognize the new font.

The upstream release remains the fallback pin in `backend-version`. Phase 2 requires API 8 from this checkout. Follow the linked main-machine guide to build and install it. An installation with the older pinned API keeps mail working and waits for API 8 before starting these inbox features. The `omamail` backend filename, data/config directories, keyring namespace, and compatibility desktop handler filename intentionally remain unchanged. This preserves Google authorizations, account registry, cache, drafts, and undo-send state. The visible application and shell plugin are Magpie. Do not run stock Omamail and Magpie simultaneously against that shared state.

## Development

Keep `upstream` pointing at huacnlee/omamail and `origin` at WebscapeOrg/magpie-mail. Changes go through a branch and PR in this fork. `make validate` runs the inherited backend, UI, and packaging checks. Magpie's behavior tests are `ui/tests/test_display.js`, `ui/tests/qml/tst_display_settings.qml`, and the single-pane navigation test in `tst_app_compose_pending.qml`.

The font-aware primitives in `ui/controls` are copies of the installed Omarchy Quattro toolkit with local typography bindings. Their upstream MIT notice is in `ui/controls/LICENSE`. They keep Omarchy's theme and interaction conventions while letting Magpie's interface size differ from the rest of the shell.

### List view refinements

The list header keeps Search, Folder, Compose and the account selector; the Magpie Mail name and Apple's ✉️ appear at the top of Menu. The content frame uses equal insets on all four edges. Dates occupy the right edge of message rows without mailbox symbols, and row action centers are 15% farther apart. Interface icons use bundled [Lucide vectors](ui/assets/lucide/README.md), with theme colors and a filled star for starred mail. Provider artwork and the Magpie bird retain their own designs.

In the list view, the mailbox selector sits beside the menu in the position used by Back when reading a message. In the single-column message reader, ← Back sits beside the menu in the top toolbar and uses the same outlined button style as Compose. Escape keeps its existing navigation behavior. Folder and the mailbox selector share the outlined toolbar style; the menu glyph is twice its former size.

Messages with file attachments show a small Lucide paperclip beside the date, with space on both sides. The indicator fits within the existing text height and does not increase the row or line height. The MIME classifier excludes inline sender logos.

Reader attachments appear as individual cards above the message actions, with a filename, file type, size and a separate Save to Downloads control. Click a card to open its file. The shelf scrolls horizontally when needed and stays bounded so the message remains readable. Image files show a static thumbnail; PDFs show their first page when the isolated Linux preview worker is available. Unsupported, oversized or unreadable files keep their named file tile and their Open and Save actions. Previews require the checkout’s API 8 backend; older backends retain the cards and normal file actions.

Contact photos fill the circular avatar. Organization logos are fitted onto a transparent square with 30% radial clearance before caching; the UI displays every prepared image at full size. LinkedIn uses its official 144 px tile and xneelo its official 300 px site icon; other organizations request up to 256 px through the existing domain-only logo service. The avatar cache revision refreshes older entries automatically. Sources: [LinkedIn brand site](https://brand.linkedin.com/) and [xneelo](https://xneelo.co.za/).

Unavailable descriptions keep the original subject and preview. Hovering the subject shows the safe failure reason and retry action. The unreleased API 8 snapshot carries the cache revision and expiry; older backends keep normal mail available without starting descriptions.

## Gmail-only accounts

Magpie uses the Gmail API for all mailboxes. Magpie Calendar owns calendars, event editing, attendance and reminders; Magpie only reads the calendar as context for The Point. Magpie opens invitations and suggested events in Magpie Calendar for review. Google Workspace custom domains and multiple accounts are supported. Add mailbox opens Google setup directly. Existing credentials, account identities, downloaded mail, drafts, aliases and calendar choices are preserved. Unsupported provider records are never converted into Gmail accounts or silently deleted.

Unified search prepares syntax once, then each account resolves its own `me` and labels. Inbox overviews reuse downloaded message content. These changes preserve the existing quota scheduler and do not increase background request concurrency.
