# Local mail backup

Enterprise's `mail-backup-export.timer` runs `~/.local/share/omamail/bin/omamail backup export --json` at 09:15 and 21:15, fifteen minutes before its scheduled restic backups. It runs separately because Time Machine limits its pre-command to sixty seconds; the existing PostgreSQL pre-command remains unchanged. This Linux command requires the installed backend to support `backup.export` (unreleased API 8). If the shared engine is enabled, the command contacts that engine; it never falls back to opening its live databases when the engine is unavailable. A stopped standalone installation can export through a temporary owner in the command itself. A store held by another process causes failure.

The archive is uncompressed, with sorted stores and messages and fixed tar metadata so restic can deduplicate unchanged content. The output is `${XDG_STATE_HOME:-~/.local/state}/omamail/mail-backup.tar`, owned by the current user with mode 0600. Keep the existing restic exclusion for `omamail/mail/**`, including its private `.backup` scratch directory. Back up the resulting archive as part of the existing state-directory source. The timer's wrapper allows 660 seconds and stores its status, successful receipt and bounded error output privately under `${XDG_STATE_HOME:-~/.local/state}/mail-backup-export/`. Run it as the desktop user, with the same XDG directories as Magpie. No credentials, network access or Gmail writes are needed to export. A failed export does not stop the separate restic job, but the current mail archive's freshness is unconfirmed.

Each archive contains `manifest.json`, plus `mail/<account-hash>/mail.sqlite` and exactly the content-addressed blobs referenced by that database. All database tables are retained, including pending offline edits, conflicts, queued fetches, search data, provider cursors and deletion records. Retained stores belonging to accounts removed from Settings are included. This protects downloaded local content; it does not claim to contain messages or attachments that were never downloaded. Account settings, drafts, outbox, retained attachments, snoozes, phone registrations and credentials are separate backup sources described in the Enterprise inventory.

SQLite's online backup API runs through the owning custom VFS connection. The writer is held during that account's database copy; other readers can continue. Each account has its own consistent snapshot instant, rather than a cross-account transaction. The destination database must pass SQLite integrity and foreign-key checks. Every referenced blob must exist, contain the correct message ID, and match its SHA-256 name. Missing or corrupt content, unsafe paths, competing export jobs and changes to the store inventory prevent publication. Blob storage is immutable and currently has no garbage collector; any future collector must coordinate with exports before removing referenced content.

A complete archive replaces the previous archive atomically. The displaced archive remains under the excluded private scratch directory until the next export, and staging is serialized by an owned process lease. Failures before publication leave the current archive unchanged. If the directory flush after replacement fails, the exporter attempts an atomic rollback. A rollback that cannot be confirmed returns `local_backup_completion_unknown`, retains the available copies and exits nonzero; do not describe that run as successful. Interrupting a client can leave the owner finishing its export, and its lease prevents another export from deleting the active staging files. The worker has a nine-minute cooperative budget, checked during database copying, writer-lock waits, content reads and hashing; SQLite validation uses an interrupt handler. The caller stops waiting after ten minutes and reports completion unknown. A kernel-level disk stall can outlast the worker budget; no export timeout kills the mail engine. In either case rerun after the owner finishes, and require a fresh successful receipt.

JSON mode uses the CLI envelope: `{"ok":true,"result":{"complete":true,...}}`. A fresh export requires exit status zero, `ok == true` and `result.complete == true`. The receipt under `result` contains the archive name, byte count, SHA-256 and per-store message and pending-edit counts. It contains no message subjects, bodies or credentials. A saved successful receipt identifies that export by its archive hash. The archive's `manifest.json` contains its creation time; a later failed or uncertain attempt does not make the current archive fresh. A complete archive on Enterprise is a local recovery copy, not evidence that restic reached DS9. Confirm a successful remote snapshot and restoration separately.

## Restoration

Restore into a private, empty temporary directory first. Never unpack over a running mail store. Check the archive against its saved SHA-256 receipt, extract only its regular files, and reject unexpected names, links or devices. Verify every database against its manifest hash, every blob against its filename, `PRAGMA integrity_check`, and `PRAGMA foreign_key_check` on these isolated copies. The maintained Rust and process tests restore exports and check pending edits, search results and content with synthetic data.

Stop Magpie's engine and all standalone backends before moving restored `mail/<account-hash>` directories into the state directory. Keep the existing store as a separate private recovery copy. Restore directories with mode 0700 and files with mode 0600, owned by the desktop user. Do not restore `.owner`, socket, WAL or journal files from a filesystem copy: the export contains the complete SQLite database and omits those transient files. Restore matching account settings separately; sign-in may be needed if the operating-system credential store was lost.

Review pending edits before allowing synchronization: an older snapshot can contain work that completed on Gmail after the snapshot was taken. Restore the outbox and phone registrations deliberately, too; an older outbox can contain already-sent messages, and an older device registry can reinstate a revoked phone. Restoring this archive does not itself dispatch mail or contact Gmail.

## Verification

`cargo test --locked --lib local_mail::backup` exercises restoration and failure preservation with private fixtures. `cargo build --locked --bin omamail` followed by `python3 tests/test_mail_backup.py` exercises the real Linux daemon and CLI, verifies the live fixture owner's lease, restores through ordinary SQLite only on the exported copy, and proves that failed exports preserve the previous complete archive. These tests do not read Dave's mail or use his credentials.
